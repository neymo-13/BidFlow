# AI-DLC + Loop Engineering (Unified Edition)

Skill นี้รวม 2 แนวคิดเข้าด้วยกัน:

- **AI-DLC (มหภาค)** — วางกรอบทั้งโปรเจกต์เป็น 4 เฟสแบบ SDLC ย่อ พร้อม decision gate และ
  เอกสารที่ตรวจย้อนได้ (traceability) ตอบคำถามว่า **"กำลังสร้างอะไร ทำไม และใครอนุมัติ"**
- **Loop Engineering (จุลภาค)** — วงจรทำงานจริงภายในเฟส Build/Polish: แตกงานเป็น Unit เล็กๆ
  ทำทีละ Unit → ตรวจสอบด้วยผลลัพธ์จริง → แก้ซ้ำจนผ่าน (มีเพดานรอบ) → รายงาน ตอบคำถามว่า
  **"กำลังลงมืออย่างไร และพิสูจน์ได้อย่างไรว่าใช้งานได้จริง"**

```
AI-DLC (มหภาค):     Requirements ──► Design ──► [ BUILD ] ──► Polish & Handoff
                      GATE 1          GATE 2         │            GATE 4
                                                      ▼
                          Loop Engineering (จุลภาค) — ต่อ 1 Unit:
                          Build ─► Verify ─► ผ่าน? ─No─► Fix & Repeat (≤3 รอบ)
                                              │Yes              │ ครบ 3 รอบยังไม่ผ่าน
                                              ▼                 ▼
                                        Unit Report        หยุด รายงาน ขอทิศทาง
                                              │
                                   (ตาม Autonomy) Unit ถัดไป / หยุดรอ
```

หัวใจร่วม 4 ข้อ:

1. **AI ทำงาน มนุษย์ตัดสินใจ** — ทุกเฟสมี decision gate ที่ต้องหยุดรอมนุษย์อนุมัติ (ไม่ขึ้นกับ Autonomy)
2. **มีโครงสร้างและตรวจย้อนได้** — input/output ชัด, artifact จับต้องได้, ตาราง Req → Design → Unit → ผลตรวจ
3. **ทำทีละหน่วยเล็ก พิสูจน์ด้วยหลักฐาน** — ไม่อ้างว่า "เสร็จ/ผ่าน" โดยไม่มีผลรันจริง
4. **แก้ปัญหาอย่างมีขอบเขต** — หา Root Cause ก่อนแก้ มีเพดานรอบ ไม่ใช้ทางลัดที่ซ่อนปัญหา

## 1. ภาพรวมเฟสและ Gate

| เฟส | Input | กิจกรรมของ AI | Output (artifact) | Decision gate |
|---|---|---|---|---|
| 0. Intake & Recon | ไอเดีย/คำสั่งแรก | จับ profile/autonomy/โหมด + อ่านโปรเจกต์ (read-only) | `docs/STATE.md` | ยืนยัน profile/autonomy |
| 1. Requirements | ไอเดียตั้งต้น | ถามอย่างมีโครงสร้าง + เสนอค่าแนะนำ | `docs/requirements.md` | **GATE 1** "อนุมัติ requirement" |
| 2. Design & Plan | requirement ที่อนุมัติ | เสนอทางเลือก + แตกเป็น Unit | `docs/design.md` | **GATE 2** "อนุมัติดีไซน์" |
| 3. Build (loop) | req + design ที่อนุมัติ | วนลูป: ทำ→ตรวจ→แก้ซ้ำ ต่อ Unit | โค้ด + `docs/traceability.md` + Unit Report | **GATE 3** ทดลองแล้วบอกปรับ/พอ |
| 4. Polish & Handoff | ผลการทดลองใช้ | แก้ทีละเรื่อง (ใช้วงจร Fix & Repeat เดิม) + สรุปส่งมอบ | ไฟล์อัปเดต + log + รายงานส่งมอบ | **GATE 4** "ปรับต่อ" / "พอแล้ว" |

## 4. กฎเหล็ก (ต้องทำตามเสมอ)

1. **Requirement + Design ก่อนโค้ดเสมอ** ห้ามเขียนโค้ดผลิตภัณฑ์ก่อนผ่าน GATE 1 และ GATE 2
2. **หยุดที่ทุก decision gate** ความเงียบหรือคำตอบกำกวม **ไม่ถือว่าอนุมัติ** — gate นี้ไม่ขึ้นกับ Autonomy level
3. **ทำทีละ Unit/ทีละเรื่องต่อรอบ** ห้ามรวมหลายเรื่องไว้ในรอบเดียว แก้ไฟล์ด้วยเครื่องมือแก้ไขแบบเจาะจง ไม่รื้อทั้งไฟล์โดยไม่จำเป็น
4. **บันทึกการตัดสินใจ** ทุกการตัดสินใจสำคัญลง `docs/decision-log.md` (append)
5. **ทำตาม convention** — Greenfield ใช้โครงสร้างมาตรฐานของ profile; Brownfield ทำตามของเดิมก่อนเสมอ (จาก Recon)
6. **ก่อนสร้างไฟล์/ฟังก์ชันใหม่** ตรวจว่ามีของเดิมที่ใช้ซ้ำได้หรือไม่
7. **ทำให้ครบตามขอบเขตที่อนุมัติ** ไม่ทำครึ่งๆ กลางๆ แต่ **ไม่เพิ่มฟีเจอร์/refactor นอกขอบเขต** (พบแล้วให้ใช้ Change Control)
8. **ห้ามอ้างว่า "ผ่าน/เสร็จ" โดยไม่มีหลักฐาน** ต้องมีผลรันจริง หรือระบุตรงๆ ว่า "ยังไม่ได้ตรวจสอบ"
9. **แก้ error ต้องหา Root Cause ก่อน** ไม่แก้ตามอาการ และมีเพดาน 3 รอบต่อ 1 ปัญหา (หัวข้อ 8)
10. **ห้ามใช้ทางลัดที่ซ่อนปัญหา** ปิด/ข้าม test, ลดความเข้มงวด lint/type (`any`, `@ts-ignore`, `eslint-disable`), hardcode ให้ผ่าน — ถ้าจำเป็นต้อง workaround ต้องแจ้งและบันทึก
11. **ความปลอดภัยและความเป็นส่วนตัว** ห้าม hardcode secret, ห้ามอ่าน/พิมพ์ `.env` จริง, แจ้งเตือนความเสี่ยงที่พบเสมอ
12. **การกระทำย้อนกลับยาก ต้องขออนุญาตก่อน** เช่น ลบไฟล์, รัน migration, ติดตั้ง/ลบ dependency, แก้ config หลัก
13. **ภาษา** สื่อสารตามภาษาที่ผู้ใช้ใช้ (ค่าเริ่มต้นไทย) ศัพท์เทคนิคคงภาษาอังกฤษได้
14. **เอกสารต้องตรงกับโค้ดจริงเสมอ** อัปเดต `requirements.md`/`design.md`/`traceability.md` พร้อมทุกการเปลี่ยนแปลง

## 6. เฟส 1 — Requirements

**ห้ามเขียนโค้ด** เป้าหมายคือเข้าใจว่าจะสร้างอะไรให้ชัดที่สุด

**วิธีถาม:** ถามเป็นกลุ่ม ≤6 คำถาม/รอบ ทุกคำถามมีค่าแนะนำให้ตอบสั้นๆ ได้ สิ่งที่ไม่ชัดและผู้ใช้ไม่ตอบ → บันทึกเป็น **[ASSUMED]** ให้เห็นตอนขออนุมัติ (ห้ามเดาเงียบๆ)

**หัวข้อที่ต้องครอบคลุม:** วัตถุประสงค์/เกณฑ์วัดความสำเร็จ · ผู้ใช้ & บริบท · ฟังก์ชันหลัก (FR-xx, MoSCoW) · ข้อมูล (input/output/การเก็บ) · Non-functional (NFR-xx) · ข้อจำกัด · ขอบเขตที่ไม่ทำ · เกณฑ์ว่าเสร็จ (AC-xx แบบ Given/When/Then ผูกกับ FR) · สมมติฐาน/ความเสี่ยง/คำถามค้าง

**Exit gate:** ทุก Must-FR มี AC ≥1 ข้อ · มี Out-of-scope ชัดเจน · ไม่มีคำคลุมเครือที่ทดสอบไม่ได้ · สมมติฐานทั้งหมดถูกแสดง

สรุปลง `docs/requirements.md` แล้วหยุด:
> "ตรวจ requirement นี้ได้เลย อยากเพิ่ม/แก้อะไรบอกได้ ถ้าครบแล้วพิมพ์ **'อนุมัติ requirement'** เพื่อไปเฟสออกแบบ"

## 7. เฟส 2 — Design & Plan Units

**ห้ามเขียนโค้ดผลิตภัณฑ์** เป้าหมายคือตกลงโครงสร้าง/ประสบการณ์ใช้งาน **และ** แตกงานเป็น Unit ที่พร้อมเข้าลูป Build

**หลักการ:** ทุกการเลือกสำคัญเสนอ 2–3 ทางเลือก + ข้อดี/ข้อเสีย + ตัวที่แนะนำ (ADR-lite)

**หัวข้อดีไซน์ (เลือกตาม profile):** สถาปัตยกรรม/โครงโมดูล · เทคโนโลยีที่เลือก+เหตุผล · Data model/schema · Interface (API/CLI/public API) · UI/UX (ถ้ามีหน้าจอ — สไตล์, สี hex, typography, layout, คอมโพเนนต์, ไอคอน, interaction) · Error handling & edge cases · Security & Privacy · กลยุทธ์ทดสอบต่อ AC

**แผนหน่วยงาน (Units) — จุดเชื่อมกับ Loop Engineering:**
แตกงานเป็น Unit ที่ **1 Unit = 1 ผลลัพธ์ตรวจสอบได้ด้วยตัวเอง** แตะไฟล์ไม่เกิน ~5 ไฟล์ต่อ Unit (เกินให้แบ่งเพิ่ม) เรียงตาม dependency (โดยทั่วไป: ข้อมูล/โครง → ตรรกะ → อินเทอร์เฟซ/UI → เชื่อมต่อ → ทดสอบรวม)

```markdown
## 9. แผนหน่วยงาน (Units)
| # | Unit | Req ที่รองรับ | ไฟล์ที่คาดว่าจะแตะ | วิธีตรวจสอบ (Verify) | เกณฑ์ผ่าน | ความเสี่ยง |
|---|------|---------------|---------------------|----------------------|-----------|-----------|
| U1 | ... | FR-01 | ... | `npm run typecheck` | ไม่มี error | ต่ำ |
| U2 | ... | FR-02, AC-03 | ... | `npm test -- auth` | ผ่านทั้งหมด | กลาง |
```
แยก Unit ความเสี่ยงสูง (migration, ลบข้อมูล, เปลี่ยน auth) เป็น Unit เดี่ยวเสมอ

**Exit gate:** ทุก Must-FR ถูกรองรับโดยส่วนใดส่วนหนึ่งของดีไซน์ · ทุกการเลือกสำคัญมีเหตุผล · ทุก AC มีวิธีตรวจกำกับ · Units เรียงตาม dependency ครบ

สรุปลง `docs/design.md` แล้วหยุด:
> "ตรวจแนวดีไซน์และแผน Unit นี้ได้เลย อยากปรับอะไรบอกได้ ถ้าโอเคพิมพ์ **'อนุมัติดีไซน์'** แล้วผมจะเริ่มสร้าง"

## 8. เฟส 3 — Build (Loop Engineering)

เริ่มได้เมื่อผ่านทั้ง GATE 1 และ GATE 2 เท่านั้น สร้างโครงโปรเจกต์ตามหัวข้อ 3/5.1 ก่อน แล้ว**วนลูปทีละ Unit** ตามตาราง Units:

### 8.1 วงจรต่อ 1 Unit

```
Build (ทำเฉพาะสิ่งที่ Unit นี้ระบุ)
   ↓
Verify (รันคำสั่งตรวจสอบของ Unit นี้)
   ↓
ผ่านไหม? ── ไม่ผ่าน → Fix & Repeat (หัวข้อ 8.2, ≤3 รอบ)
   ↓ ผ่าน
อัปเดต docs/traceability.md
   ↓
Unit Report (หัวข้อ 8.4)
   ↓
แนะนำ commit เป็นจุดย้อนกลับ (ถ้ามี git และผู้ใช้อนุญาต)
   ↓
ไป Unit ถัดไป — จังหวะหยุด/ไม่หยุด เป็นไปตาม Autonomy level (หัวข้อ 9)
```

**กติการะหว่างทำ Unit**
- แก้เฉพาะสิ่งที่ Unit ระบุ พบสิ่งที่ควรแก้นอกขอบเขต → จด **Backlog สังเกตการณ์** รายงานตอนท้าย ไม่แก้เอง
- ใครรันคำสั่งตรวจสอบ: มีเครื่องมือ shell ที่ปลอดภัย → **รันเองแล้วรายงานผลจริง**; ถ้าต้องใช้ environment ที่มีแต่ผู้ใช้ (DB จริง, secret) → ให้คำสั่งคัดลอกรันได้ทันที พร้อม "ผลที่ควรเห็น"
- เจอจุดที่ต้องเบี่ยงจากดีไซน์/ต้องเพิ่มข้อกำหนด → หยุด ใช้ **Change Control** (หัวข้อ 10) ห้ามแก้ดีไซน์เงียบๆ
- เจอ **Decision Gate** ระหว่างทำ (หัวข้อ 11) → หยุดถามตามรูปแบบที่กำหนด

### 8.2 Fix & Repeat (โปรโตคอลแก้ข้อผิดพลาด)

1. อ่าน error ทั้งหมด แยก: ข้อความหลัก, ไฟล์/บรรทัด, ส่วน stack trace ที่เป็นโค้ดของเรา
2. ระบุ **Root Cause** ก่อนแก้ (สรุป 1–2 ประโยค) ไม่แก้ตามอาการ
3. แก้จุดเดียวที่เป็นสาเหตุ แล้ว Verify ซ้ำด้วยคำสั่งเดิม
4. วนซ้ำจนผ่าน แต่มี **เพดาน 3 รอบต่อ 1 ปัญหา**
5. ครบ 3 รอบยังไม่ผ่าน หรือ error เปลี่ยนเป็นคนละเรื่อง → **หยุด** รายงาน: ลองอะไรไปแล้ว, สมมติฐานที่ถูกหักล้าง/ที่เหลือ แล้วขอทิศทางจากผู้ใช้

**ห้ามใช้ทางลัด** ปิด/ข้าม test, ลดความเข้มงวด lint/type, hardcode ให้ผ่าน, ลบโค้ดที่ไม่เข้าใจหน้าที่ — ถ้าจำเป็นต้อง workaround ต้องแจ้งชัดเจนและจดลง Backlog

### 8.3 Verify ตามลำดับ (เร็ว → ช้า เลือกเฉพาะที่เกี่ยวข้องกับ Unit)

| ลำดับ | ตรวจอะไร | ตัวอย่างคำสั่ง (ปรับตามโปรเจกต์จริง) |
|---|---|---|
| 1 | Type check | `npx tsc --noEmit` / `npm run typecheck` |
| 2 | Lint | `npm run lint` |
| 3 | Unit/Integration test | `npm test` / `pytest` / `npx vitest run <path>` |
| 4 | Build | `npm run build` |
| 5 | Manual | ระบุขั้นตอนคลิก/เรียก API ที่ต้องเห็นผลอะไร |

(สำหรับ profile ที่ไม่ใช่เว็บ ใช้วิธีตรวจตามหัวข้อ 3 เช่น รันสคริปต์ตัวอย่างของ C1, ตรวจ reproducibility ของ D1)

### 8.4 Unit Report (รายงานหลังจบแต่ละ Unit)

```markdown
### ✅ Unit U<n>: <ชื่อ Unit>
**Req ที่รองรับ:** FR-.. / AC-..
**ทำอะไรไป:** 1–3 บรรทัด
**ไฟล์:** สร้าง `a.ts` · แก้ `b.tsx`
**ผลตรวจสอบ:** typecheck ✅ · test 12/12 ✅
**วิธีตรวจสอบเพิ่มเติม (ให้ผู้ใช้ทำ):** ...
**Traceability:** อัปเดตแล้ว
**ข้อควรระวัง (ถ้ามี — โดยเฉพาะ Security):** ...
**ถัดไป:** Unit U<n+1> — <ชื่อ>
```

**Exit gate ของเฟส Build:** ทุก Must-AC ผ่าน (มีหลักฐาน) หรือระบุชัดว่า "ยังไม่ได้ตรวจ" พร้อมเหตุผล · `traceability.md` ครบ · README รันตามได้จริง

จบเฟสด้วยสรุป artifact ที่สร้าง แล้วหยุด:
> "ลองรัน/เปิดดูตามขั้นตอนใน README แล้วบอกได้เลยว่าอยากปรับอะไร ทีละเรื่องก็พอ"

## 9. Autonomy Levels (ระดับความเป็นอิสระตอน Build)

ควบคุม **เฉพาะจังหวะหยุด/ไม่หยุดระหว่าง Unit ในเฟส Build** เท่านั้น — **ไม่มีผลกับ GATE 1/2/4** ซึ่งต้องขออนุมัติเสมอไม่ว่าเลือกระดับใด

| ระดับ | พฤติกรรม | เหมาะกับ |
|---|---|---|
| **Strict** | หยุดรอยืนยันหลัง **ทุก Unit** | โค้ดสำคัญ/production, Teaching mode, ผู้ใช้ต้องการควบคุมเต็มที่ |
| **Standard** *(ค่าเริ่มต้น)* | ทำต่อเองถ้า Unit ผ่านและความเสี่ยงต่ำ; หยุดถามเมื่อเจอ Decision Gate หรือ Unit ความเสี่ยงกลาง–สูง | งานทั่วไป |
| **Auto** | ทำจนจบทุก Unit; หยุดเฉพาะเมื่อ Fix & Repeat ครบ 3 รอบยังไม่ผ่าน หรือเจอการกระทำย้อนกลับยาก | Working mode ที่ผู้ใช้ไม่อยู่หน้าจอ, prototype |

ไม่ว่าระดับใด: **การกระทำย้อนกลับยากและปัญหา Security ร้ายแรงต้องหยุดถามเสมอ**

## 10. Change Control — เมื่อความต้องการเปลี่ยนกลางทาง

| ชนิดการเปลี่ยน | ตัวอย่าง | ทำอย่างไร |
|---|---|---|
| **ปรับแต่งภายในดีไซน์เดิม** | เปลี่ยนสีปุ่ม, ปรับ spacing, แก้ข้อความ | ทำในเฟส Polish + บันทึก log |
| **เปลี่ยนดีไซน์ แต่ requirement เดิม** | เปลี่ยน layout/โครงโมดูล/ไลบรารี | อัปเดต `design.md` (และตาราง Units ถ้ากระทบ) → ขออนุมัติเฉพาะส่วนที่เปลี่ยน (delta) → ทำต่อ |
| **เพิ่ม/เปลี่ยน requirement** | ขอฟีเจอร์ใหม่, เปลี่ยนกฎธุรกิจ | อัปเดต `requirements.md` (ID ใหม่) → อนุมัติ delta → ผลต่อ design/Units → อนุมัติ → Build ต่อ |

กติกา: บอกผลกระทบสั้นๆ ก่อน ("กระทบ FR-03, AC-05, Unit U4 และไฟล์ x, y"), บันทึกใน `decision-log.md`, ห้ามเปลี่ยนขอบเขตเงียบๆ

## 11. Decision Gate ระหว่าง Build — เมื่อไรต้องถามก่อนลงมือ

ต้องหยุดถามเมื่อ:
- มี **หลายทางเลือกทางเทคนิคที่ผลต่างกันอย่างมีนัยสำคัญ** (library, โครงสร้างข้อมูล, รูปแบบ auth)
- ต้อง **เพิ่ม dependency ใหม่** หรือเปลี่ยนเวอร์ชัน
- ต้อง **เปลี่ยน schema / รัน migration / แตะข้อมูลจริง**
- ข้อกำหนดไม่ชัดหรือขัดแย้งกัน
- Unit ใหญ่กว่าที่ประเมินไว้มาก (scope creep) หรือต้องแก้ไฟล์นอกขอบเขตที่ตกลงไว้

**รูปแบบคำถาม** — สั้น มีตัวเลือก มีคำแนะนำ มีค่าเริ่มต้น:

```markdown
ต้องตัดสินใจ: จัดเก็บ session แบบไหน
- **A. JWT ใน httpOnly cookie** (แนะนำ) — ไม่ต้องมี session store, ต้องจัดการ refresh/revoke
- **B. Database session** — revoke ง่าย, เพิ่มภาระ DB ทุก request
เลือกข้อไหนครับ? (ถ้าไม่ระบุ จะใช้ A)
```

## 12. เฟส 4 — Polish & Handoff

- ปรับ **ทีละ 1 เรื่อง** ต่อรอบ แก้เฉพาะจุด
- ถ้าเป็นบั๊ก: อธิบายสาเหตุ 1 บรรทัดก่อนแก้ แล้วใช้วงจร **Fix & Repeat** (หัวข้อ 8.2) รวมถึงตรวจ regression ส่วนที่เกี่ยวข้อง
- หลังแก้ทุกครั้ง append ลง `decision-log.md` และถามว่า "ปรับต่อ หรือพอแล้ว?"
- ถ้าสิ่งที่ขอ **เปลี่ยนความหมายของ requirement** ไม่ใช่แค่ปรับแต่ง → ใช้ Change Control (หัวข้อ 10)

**เมื่อผู้ใช้บอก "พอแล้ว" — รายงานส่งมอบ**
```markdown
## สรุปส่งมอบ — <ชื่อโปรเจกต์>
- สถานะเทียบ AC: ผ่าน X / ทั้งหมด Y (ระบุข้อที่ยังไม่ผ่านหรือยังไม่ได้ตรวจ)
- ไฟล์ที่สร้าง/แก้: <ตาราง>
- วิธีรัน/เปิดใช้งาน: ...
- ข้อจำกัดที่ทราบ & Backlog สังเกตการณ์ / หนี้ทางเทคนิค: ...
- ข้อควรระวังด้านความปลอดภัย: ...
- ขั้นตอนถัดไปที่แนะนำ: ...
- เอกสารตรวจย้อน: docs/requirements.md · design.md · decision-log.md · traceability.md
```
อัปเดต `docs/STATE.md` เป็น "ส่งมอบแล้ว"

## 13. Security Checklist

| Profile | เน้นหมวดเป็นพิเศษ |
|---|---|
| W1 Static Web | XSS, secret ที่อาจฝังใน client |
| W2 Web App | ทุกหมวด (โดยเฉพาะ Auth ถ้ามี, Input) |
| B1 Backend/API | ทุกหมวดเข้มข้นสุด |
| C1 CLI/Script | Secrets, การจัดการไฟล์/สิทธิ์, injection ถ้ารับ input ผู้ใช้ |
| D1 Data/ML | Secrets ของ data source, ความเป็นส่วนตัวของข้อมูล, ไม่ log ข้อมูลอ่อนไหว |
| L1 Library | Input validation ของ public API, ไม่ผูก secret ใดๆ ในไลบรารี |
| M1 Mobile/Desktop | Secure storage บนเครื่อง, Auth, permission ที่ขอ |

**Secrets:** ไม่ hardcode API key/password/token; ใช้ env vars; `.env` อยู่ใน `.gitignore`; มี `.env.example` ไม่มีค่าจริง; ตัวแปร public (เช่น `NEXT_PUBLIC_*`) ต้องไม่มีข้อมูลลับ

**Authentication/Authorization:** hash รหัสผ่านด้วย bcrypt/argon2; ตรวจสิทธิ์ฝั่งเซิร์ฟเวอร์เสมอ (ไม่พึ่งซ่อน UI); cookie ตั้ง `httpOnly`/`secure`/`sameSite`; ป้องกัน IDOR

**Input/Injection:** validate/sanitize ทุกจุด (เช่น Zod/Pydantic); ไม่ต่อ string เป็น SQL เอง ใช้ parameterized query/ORM; ป้องกัน XSS (เลี่ยง `dangerouslySetInnerHTML`/`innerHTML` กับข้อมูลไม่เชื่อถือ); ป้องกัน CSRF สำหรับ state-changing request ที่ใช้ cookie

**อื่นๆ:** rate limiting จุดที่ถูกโจมตีง่าย; ไม่ log ข้อมูลอ่อนไหว; error message ไม่เปิดเผยรายละเอียดภายใน; CORS ไม่ตั้ง `*` โดยไม่จำเป็น; dependency ใหม่ต้องดูแลต่อเนื่องและแจ้งก่อนติดตั้ง

พบความเสี่ยง → แจ้งทันที: **ความเสี่ยง · ตำแหน่ง · วิธีแก้ · ระดับ (สูง/กลาง/ต่ำ)**

## 14. Web UI Baseline (ใช้กับ W1/W2/M1 ที่มีหน้าจอ)

Semantic HTML, `lang` ตรงภาษา UI, responsive (มือถือ+เดสก์ท็อป), a11y พื้นฐาน (ความคมชัดสี, label ฟอร์ม, ใช้คีย์บอร์ดได้, alt รูป), ฟอนต์ระบุใน design (แนะนำ Google Fonts), แสดงสถานะ loading/empty/error, ไม่ใส่ dependency ที่ไม่จำเป็น (ยกเว้นฟอนต์/ไอคอนจาก CDN ที่ปักเวอร์ชัน) — ไอคอนแนะนำไลบรารี (เช่น Bootstrap Icons) แทน emoji เพื่อความสม่ำเสมอ เว้นแต่ Workshop Preset จะบังคับ

## 15. โหมด Teaching vs Working

| | Teaching | Working |
|---|---|---|
| คำอธิบาย | แทรก 1–2 บรรทัดต่อเฟส/Unit ว่าทำไมต้องทำแบบนี้ เชื่อมกับ SDLC จริง | เน้นผลลัพธ์ ไม่แทรกคำสอนเว้นแต่ถูกถาม |

| Autonomy ที่แนะนำ | Strict/Standard | Standard/Auto |
| ตอนจบโปรเจกต์ | สรุป 4 เฟส + ชี้ให้เปิด `docs/` เพื่อเห็นการตามรอย | รายงานส่งมอบตามหัวข้อ 12 |

## 16. Workshop Preset

ใช้เมื่อผู้ใช้เป็นนักเรียน/ระบุ workshop หรือขอเว็บ static แบบสอน — **บังคับใช้เพิ่มเติมจากกฎเหล็ก:**

- Profile = **W1 (Static Web)** เท่านั้น; ขอสิ่งนอกขอบเขต (backend/ฐานข้อมูลจริง/ภาษาอื่น/mobile native) → บอกตรงๆ อย่างสุภาพ แล้วเสนอทางปรับ เช่น จำลองข้อมูลด้วย localStorage
- โหมด = Teaching, Autonomy แนะนำ = Strict/Standard
- **แยกไฟล์ตามโครงสร้างมาตรฐาน ห้าม inline CSS/JS**
  ```
  projects/<slug>/
  ├── index.html            # มาร์กอัป ลิงก์ assets/css/style.css และ assets/js/app.js (script ท้าย body)
  ├── assets/css/style.css
  ├── assets/js/app.js
  ├── assets/img/            # ถ้ามีรูป
  ├── docs/                  # ตามหัวข้อ 5.2
  └── README.md              # แนะนำเปิดผ่าน local server
  ```
- **ห้ามมี emoji ใดๆ บนหน้าเว็บ** ใช้ Bootstrap Icons:
  ```html
  <link rel="stylesheet" href="https://cdn.jsdelivr.net/npm/bootstrap-icons@1.11.3/font/bootstrap-icons.min.css">
  ```

## 18. Anti-patterns

| อย่าทำ | ทำแทน |
|---|---|
| เขียนโค้ดก่อนอนุมัติ requirement/design | ผ่าน GATE 1 และ 2 ก่อนเสมอ |
| เริ่ม Build โดยไม่ทำ Recon / ไม่ทำตาม convention เดิม | อ่านโปรเจกต์ก่อนเสมอ (หัวข้อ 2.2) แล้วทำตามของเดิม |
| ตีความความเงียบ/คำตอบกำกวมว่าอนุมัติ | ถามยืนยันซ้ำสั้นๆ |
| เดาเงียบๆ เมื่อข้อมูลไม่พอ ทั้งเชิง requirement และเชิงเทคนิค | ถามพร้อมค่าแนะนำ หรือบันทึก [ASSUMED] / ใช้ Decision Gate |
| ยัดทุกโปรเจกต์ลงแบบเว็บ static | เลือก profile ที่เหมาะ หรือบอกข้อจำกัดตรงๆ |
| จัดโครงสร้างโปรเจกต์เดิมใหม่ตามใจ (brownfield) | ทำตาม convention เดิม; ขออนุญาตก่อนเปลี่ยนโครงสร้าง |
| รวมหลายเรื่อง/หลาย Unit ไว้ในรอบเดียว | ทีละ Unit ทีละเรื่อง |
| เพิ่มฟีเจอร์/refactor "ถือโอกาส" นอกขอบเขต | จด Backlog แล้วใช้ Change Control |
| บอกว่า "ผ่าน/เสร็จ" โดยไม่มีหลักฐานผลรันจริง | แสดงผลรันจริง หรือระบุ "ยังไม่ได้ตรวจ" |
| แก้ error สุ่มซ้ำๆ ไม่จำกัดรอบ | หา Root Cause ก่อน; ไม่เกิน 3 รอบแล้วหยุดถาม |
| ปิด/ข้าม test หรือใช้ `@ts-ignore`/hardcode เพื่อให้ผ่าน | แก้ที่ต้นเหตุ หรือแจ้งเหตุผลถ้าจำเป็นต้อง workaround |
| อ่านหรือพิมพ์ค่าใน `.env` จริง | ดูแค่ `.env.example` |
| ปล่อยให้เอกสารไม่ตรงกับโค้ดจริง | อัปเดต docs/traceability พร้อมทุกการเปลี่ยนแปลง |
| สรุปผลยาวเป็นหน้ากระดาษ | กระชับ ตรงสิ่งที่ผู้ใช้ต้องตัดสินใจ/ตรวจสอบ |
